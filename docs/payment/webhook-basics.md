# Webhook / async callback pattern, in the amount of depth BOOK-55 needs

Deliberately general — no BookIt specifics. For what this project's provider mock and
saga actually look like today, see `payment-decisions.md`; for the crash-window this
doc's §4 closes, see `saga-basics.md` §6, which named BOOK-55 as the fix while building
BOOK-54.

## 0. The mental model, if you remember nothing else

```
 Synchronous call                        Async callback (webhook)

 BookIt ──"charge $200"──> Provider       BookIt ──"charge $200, ref=abc-123"──> Provider
 BookIt <──"SUCCESS"────── Provider       BookIt <──"ok, working on it"───────── Provider
                                                          ...time passes...
 one request, one response,               Provider ──"ref=abc-123, SUCCESS"──> BookIt
 answer known immediately                 the answer arrives later, as its own
                                           inbound request BookIt didn't initiate
```

A webhook is nothing more exotic than an HTTP endpoint on *your* server that someone
else's system calls. The only thing that makes it a "webhook" rather than an ordinary
endpoint is *who* is expected to call it and *when* — an external system, at a time of
its own choosing, to report something that finished after the original request already
returned.

## 1. Why a real async provider can't just answer inline

A mock that returns `SUCCESS`/`FAILURE` directly from `charge()` is standing in for a
simplification real providers don't get to make: actually charging a card can involve
steps the provider's own system doesn't finish inside the time budget of one HTTP
request — bank authorization, fraud review, retries against a card network. A provider
built this way has exactly two ways to tell the caller what eventually happened:

- **Polling** — the caller keeps asking "did it finish yet?" until the answer changes.
- **Callback (webhook)** — the caller registers "call me here when you know," and the
  provider makes an outbound request of its own once it does.

Neither is universal — some APIs are genuinely synchronous, some support both — but
once an operation's real-world completion time isn't bounded by one request's lifetime,
something has to give: either the caller waits/asks repeatedly, or the provider reports
back independently.

## 2. Correlation id — the one thing that makes a callback answerable at all

The moment the answer arrives in its own, later, independent request, it has to say
*which* earlier request it's the answer to — a provider serving many callers has no
other way to know. That identifier is the correlation id: a value the caller mints and
hands over **at the start of the call**, which the provider is expected to echo back
verbatim whenever it reports the outcome.

```
BookIt                         Provider
  │  charge, correlation_id=abc-123     │
  ├─────────────────────────────────────>│
  │                                      │  ...processing...
  │  webhook: correlation_id=abc-123,    │
  │  outcome=SUCCESS                     │
  │<─────────────────────────────────────┤
```

**Why it has to be minted before the call, not read back from a row afterward:** the
whole point of the id is to survive a gap where the caller's own bookkeeping might not.
If the caller instead used an id generated by inserting a database row *after* the call
succeeds, a crash between "the provider accepted the charge" and "the row got written"
leaves the eventual webhook with a correlation id nothing in the caller's database will
ever match — the exact failure this pattern exists to avoid (§4).

## 3. Webhook vs. polling vs. a persistent connection — three different answers to "how do I find out later"

| | Who initiates each check | Shape |
|---|---|---|
| Polling | The caller, repeatedly | Separate request/response pairs, "did it finish yet?" asked again and again |
| Webhook | The provider, once (per outcome) | One inbound HTTP request, sent when the provider actually has an answer |
| Persistent connection (WebSocket, SSE) | Neither, after the initial handshake | One connection stays open; either side can send over it at any time |

A webhook trades the caller's repeated asking for the provider's one, later, self
-initiated call — cheaper than polling when the provider is willing to make it, since
nothing is queried before there's an answer to give. It's a plain HTTP request, not a
standing connection: after that one request completes, there's nothing left open on
either side. A persistent connection solves a different problem — many updates over
time on one channel — and requires infrastructure (a kept-alive connection, reconnect
logic) a single eventual outcome doesn't need.

## 4. The gap a webhook closes that no amount of local ordering can

Splitting a caller's own steps into careful local transactions (`saga-basics.md` §2, §6)
fixes failures *within* the caller's own process — a later step failing no longer erases
an earlier one's committed record. It cannot fix one specific window: the caller's
process dying **between the provider accepting the call and the caller's own commit of
that fact landing**. In that window, the provider's side effect already happened —
nothing committed on the caller's end has any way to know that yet.

A webhook is the one mechanism that reaches into that exact gap, because it doesn't
depend on the caller having survived long enough to record anything:

```
1. BookIt → Provider: charge, correlation_id=abc-123
2. Provider charges the card successfully
3. 💥 BookIt crashes before writing anything down
4. BookIt restarts
5. Provider → BookIt: webhook, correlation_id=abc-123, outcome=SUCCESS
6. BookIt looks up abc-123, finds the right payment, reacts to it now
```

The webhook is the provider's own, independent report of what it actually did — true
regardless of what the caller was doing (or not doing) at the time. This only works if
the correlation id was hooked up *before* the crash could happen (§2) — a webhook
arriving with an id that was never durably recorded anywhere still has nothing to
attach itself to.

## 5. What actually happens if the receiver is down when the provider tries to deliver

§4's crash-recovery story has one more moving part worth being explicit about: what if
the caller is *still* down at the exact moment the provider attempts delivery, not just
during the gap before it?

```
10:00  BookIt → Provider: charge
       Provider charges the card — SUCCESS

10:01  💥 BookIt crashes

10:02  Provider → POST /payments/webhook   ✗ connection refused, BookIt is down
```

A webhook is not a fire-and-forget notification that's lost the instant the receiver
happens to be unreachable — a real provider treats "delivery failed" as its own problem
to retry, not the caller's problem to have prevented. It keeps the event queued on its
own side and tries again, typically with backoff, until it gets a successful response:

```
10:02  webhook attempt → ✗
10:03  webhook attempt → ✗
10:05  webhook attempt → ✗
10:10  webhook attempt → ✓  (BookIt is back up)
```

So the guarantee a webhook actually gives isn't "the receiver must be alive at the
instant the event happens" — it's "the provider keeps attempting delivery until the
receiver acknowledges it, however long that takes." That reframing matters, because it
means the receiver being briefly down is an *expected*, handled case, not a failure
mode the design has to work around some other way.

## 6. Why this makes idempotency non-optional, not just good hygiene

The retry behavior in §5 is exactly what makes §7's idempotency requirement inevitable
rather than a nice-to-have. The provider retries *because it can't tell the difference*
between "the request never arrived" and "it arrived, was processed, but the response
back to me got lost":

```
Provider → webhook → BookIt
                        │ processes it fully
                        │
                        ✗ 💥 crash before sending the HTTP response back

Provider: "never got a confirmation — better resend it"

Provider → webhook → BookIt   (same event, sent again)
Provider → webhook → BookIt   (and again, if this one is also lost)
```

From the provider's side, both "lost on the way in" and "lost on the way out" look
identical — no response arrived in time. It has no way to ask "did you actually finish
that, or not?", so the only safe assumption on its end is "resend, just in case." That
means a webhook handler *will* see the same logical event more than once, as a normal
consequence of how delivery works, not an edge case — which is exactly the discipline
§7 covers.

## 7. A webhook can arrive more than once — same discipline as any other inbound message

Nothing about a webhook guarantees exactly-once delivery — the provider may retry a
webhook call that timed out on its end, or that the receiver acknowledged too slowly.
A webhook handler is a consumer of an at-least-once channel, the identical shape
`inbox-basics.md` already covers for message brokers: check whether this correlation
id has already been resolved before acting on it again, and treat "already resolved" as
a no-op rather than redoing whatever reacting to the outcome does. Skipping this check
turns an ordinary provider retry into a duplicate confirmation, refund, or cancellation.

## 8. The one thing a webhook needs that a normal endpoint doesn't: proving who's calling

Every other endpoint in a typical app authenticates *its own users* — a logged-in guest,
a staff member. A webhook has no logged-in caller at all; the caller is another
system, and the endpoint is otherwise open to the internet. Without some way to verify
the request really came from the expected provider, anyone who can guess or find the
URL could call it and, say, mark an unpaid reservation as paid.

Real providers solve this with a **signature**, not a login: the payload is signed with
a secret only the provider and the receiver know (often HMAC over the raw request
body), sent in a header, and the receiver recomputes and compares it before trusting
anything in the payload. This is a different trust mechanism from `Authorization:
Bearer <token>` — there's no user session to check, only "does this request's signature
match what only the real provider could have produced."

## Cheat sheet

| Term | Meaning |
|---|---|
| Webhook | An HTTP endpoint on the caller's own server that an external system calls, on its own schedule, to report something |
| Correlation id | An id the caller mints and hands over *before* the external call, echoed back in the eventual callback so the caller knows which request it answers |
| Why mint it up front | So a crash between the external call and the caller's own bookkeeping still leaves an id the later webhook can match against |
| Polling vs. webhook vs. persistent connection | Caller asks repeatedly / provider calls back once when ready / a connection both sides can use anytime |
| The gap only a webhook closes | The caller's process dying between the external effect happening and the caller durably recording it — the webhook is independent of whether the caller survived |
| Receiver down at delivery time | Not a lost event — the provider keeps retrying (with backoff) until it gets a successful response, however long that takes |
| Why retries are inevitable, not optional | The provider can't tell "never arrived" apart from "arrived, but the response back was lost" — so the only safe move on its end is to resend |
| Webhook delivery is at-least-once | The same inbox discipline applies: check if this correlation id was already resolved before acting again |
| Authenticating the caller | No user session to check — verify a signature (e.g. HMAC over the raw body) proving the request came from the real provider, not anyone who found the URL |
